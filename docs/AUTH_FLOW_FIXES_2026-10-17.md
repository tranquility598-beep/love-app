# Регистрация и сетевые ошибки входа

Статус: изменения подготовлены локально. Production и установщики в рамках
этого исправления не обновлялись.

## Что обнаружено

- Desktop IPC выдавал транспортный `fetch failed` как HTTP 500. UI показывал
  внутренний текст ошибки, не отличая потерю соединения от ответа сервера.
- Следующий запрос к тому же auth endpoint отменял предыдущий POST, хотя
  сервер мог уже отправить письмо или принять одноразовый код.
- Вход и подтверждение ожидали внешний GeoIP без таймаута.
- Повторная регистрация удаляла неподтверждённую запись и создавала новую.
  Ошибочную почту нельзя было исправить на экране кода.
- Проверки кода и запросы писем делили один счётчик. Правильный пароль при
  неподтверждённой почте тоже расходовал лимит входа; ответы не сообщали
  точное оставшееся время IP блокировки.

Логи production подтверждают ограничения регистрации и ожидания повторного
письма. Точную транспортную причину конкретного `fetch failed` по ним
определить нельзя.

## Изменения

- IPC ограничивает время запроса и отличает сетевую ошибку от HTTP ответа.
  Новый POST авторизации не отменяет предыдущий.
- `GET /api/auth/capabilities` сообщает о поддержке безопасного повтора.
  Новый клиент делает один автоматический повтор только сетевой ошибки,
  используя тот же `X-Auth-Request-Id`. Старый backend автоматически не
  повторяется. HTTP 400/401/403/429/500 не повторяются.
- Сервер хранит ответ auth POST в памяти одного процесса до трёх минут.
  Повтор с теми же IP, идентификатором и телом получает исходный ответ,
  включая сессию после принятия OTP. Другой payload с тем же ключом — 409.
  Данные и токены не записываются на диск. CORS разрешает новый заголовок.
- Проверка OTP атомарно переводит неподтверждённый аккаунт в подтверждённый.
  Обычный запрос подтверждения не применяется к уже подтверждённым аккаунтам.
- GeoIP ограничен 1,2 секунды и кэшируется; сбой провайдера оставляет
  местоположение неизвестным. IP берётся из настроенной Express политики proxy.
- Правильный вход продолжает действующий запрос подтверждения, сохраняя код
  и признак первого входа. Повтор регистрации требует исходный пароль и
  сохраняет ту же запись пользователя.
- `POST /api/auth/registration-email` исправляет почту той же регистрации.
  Требует отдельный JWT на 20 минут, связанный с пользователем и текущей
  почтой. Он выдаётся после регистрации или правильного пароля, работает
  только для неподтверждённого аккаунта без Google и не даёт доступ к API
  сессии. Старая почта и старый токен перестают подходить после изменения.
- Проверка кода и отправка писем имеют отдельные лимиты. Успешный вход,
  включая переход к подтверждению, не расходует лимит неверных паролей.
  Регистрация ограничена 15 запросами за 15 минут с IP. Сервер сообщает
  `retryAfter` в секундах; UI показывает обратный отсчёт и блокирует повтор.
- Ошибка доставки письма открывает экран незавершённой регистрации с
  возможностью исправления адреса и повторной отправки.

Кэш повторов рассчитан на текущий production с одним процессом backend.
При переходе к нескольким процессам/репликам нужен общий защищённый кэш.
Перезапуск процесса сбрасывает кэш.

## Проверка

`node --test server/tests/*.test.js` — существующие и новые серверные проверки.
Результат проверки: 44 теста пройдены, ошибок нет.
Новые auth тесты используют тестовые модели и почтовый сервис: к реальным
аккаунтам и отправке писем не обращаются.

Дополнительно проверен UI в DOM окружении: исправление почты, блокировка
двойного submit, сохранение цифр OTP при сетевой ошибке, таймер повторной
отправки и разблокировка кнопки входа после `retryAfter`.

Для ручной проверки в локальном приложении: `npm start`, регистрация с
тестовой почтой, кнопка «Ошиблись в почте? Изменить адрес» на экране OTP,
ввод кода с исправленной почты. Нужны доступная dev база и настройки почты.

## Выпуск

Сначала обновляется backend с middleware повтора, новой возможностью смены
почты и разрешением заголовка CORS. Затем выпускается desktop клиент:
изменён главный процесс Electron, поэтому одного обновления серверной
статики недостаточно. В архив нужно включить `client/api-proxy.js`.
Профильный билдер и другие накопленные локальные изменения требуют
отдельного решения о включении в релиз.
