## 1. Критические риски (безопасность)

### 1.1. Статические TURN credentials в публичном клиентском коде
- **Факты:**
  - `client/js/voice.js`, строки 116–146: захардкожены `turn:87.199.197.158:3478` (UDP и TCP) с постоянными `username`/`credential`, плюс fallback на `free.expressturn.com`.
  - Файл доступен в **публичном** GitHub-репозитории `tranquility598-beep/love-app`; credentials присутствуют в истории Git.
  - Публичный установщик `Love-Setup-2.0.6.exe` содержит те же данные (проверено распаковкой `app.asar`).
- **Риск:** любой желающий может использовать coturn-сервер как открытый релей — счета за трафик VDS, злоупотребление, возможная блокировка хостером.
- **Исправление:**
  1. Перевести coturn на REST API с временными credentials (`use-auth-secret` + `static-auth-secret` на стороне coturn; сервер выдаёт `username=timestamp:user` и HMAC-подписанный credential через защищённый endpoint, TTL ~24 ч).
  2. Сменить текущие `username`/`credential` на coturn (компрометированы навсегда).
  3. Убрать секреты из `voice.js`; credentials запрашивать у API при инициализации звонка.

### 1.2. Backend-порт 5555 открыт напрямую в интернет
- **Факты:** `http://87.199.197.158:5555/api/health` отвечает извне; приложение слушает `0.0.0.0`. Трафик в обход Nginx идёт без TLS.
- **Риск:** обход TLS/заголовков безопасности Nginx, прямая атака на Express, утечка служебных ответов.
- **Исправление:** закрыть порт на firewall (`ufw deny 5555` / аналог) и привязать приложение к `127.0.0.1` (например, `HOST=127.0.0.1` в production env + `server.listen(PORT, HOST)`).

### 1.3. Production `.env` в локальной Electron-сборке
- **Факты:** `build/dist/win-unpacked/resources/server/.env` существует локально (production-конфигурация попала в сборку из-за `build.files`/`extraResources` в `package.json`). **Публичный релиз v2.0.6 чист** — `.env` в нём не обнаружен (проверено распаковкой установщика и содержимым `app.asar`).
- **Риск:** повторная случайная публикация локальной сборки или передача `build/` третьим лицам = утечка всех production-секретов (MongoDB URI, Cloudinary, JWT и т.д.).
- **Исправление:**
  1. Явно исключить `.env` в electron-builder: `!**/.env` и `!**/.env.*` в `build.files` и `build.extraResources`.
  2. Удалить `build/dist/win-unpacked/resources/server/.env` и добавить проверку «в артефакте нет `.env`» в release-workflow (шаг, падающий при обнаружении).

## 2. Высокие риски (данные и восстановление)

### 2.1. Вложения >5 МБ и видео хранятся локально на VDS
- **Факты:** `server/routes/upload.js` — файлы больше 5 МБ и все видео пишутся на диск VDS (`server/uploads`, `server/private-uploads`), а не в Cloudinary.
- **Риск:** backup MongoDB не восстановит вложения; заполнение диска приведёт к отказу всего сервиса; потеря VDS = потеря всех медиа.
- **Исправление:** мигрировать все вложения в Cloudinary (или S3-совместимое хранилище); до миграции — как минимум включить `uploads` в регулярный offsite-backup и настроить алерт на заполнение диска (>80%).

### 2.2. Backup: только при деплое, локально, без restore
- **Факты:**
  - Единственный backup-механизм — `server/scripts/backup-admin-v1.js`, запускается как pre-deploy шаг; копии в `/var/backups/love` на том же VDS.
  - Cron/systemd-таймеров для регулярного backup не обнаружено.
  - `mongorestore`/restore-скриптов в репозитории нет; restore drill никогда не выполнялся.
  - `mongod` на VDS **inactive** → production-БД внешняя (MongoDB Atlas). Backup встроенными средствами Atlas не подтверждён — требует проверки в консоли Atlas (вне зоны доступа аудита).
- **Риск:** при отказе между деплоями теряются все данные с момента последнего релиза; при отказе VDS теряются и сами копии; работоспособность копий не доказана.
- **Исправление:**
  1. Подтвердить/включить Cloud Backups в Atlas (continuous или daily snapshots).
  2. Ежедневный cron на VDS (независимо от деплоев) + выгрузка копии вне VDS (Object Storage / второй сервер / локальная машина).
  3. Написать `restore`-скрипт и выполнить тестовое восстановление на staging-БД (restore drill). Без успешного drill backup считается отсутствующим.

### 2.3. Health-check не отражает состояние БД
- **Факты:** `GET /api/health` возвращает `status: ok` без проверки `mongoose.connection.readyState`; при падении MongoDB мониторинг считает систему здоровой.
- **Исправление:** в `/api/health` добавить проверку `readyState === 1` (и при необходимости ping Cloudinary); при деградации — HTTP 503. Это дёшево и сразу делает мониторинг честным.

## 4. Рекомендуемый порядок исправлений

Приоритет: безопасность → сохранность данных → наблюдаемость.

1. **Ротация TURN credentials** (смена секретов на coturn) → перевод клиента на временные credentials через API. *До ротации текущие секреты считать скомпрометированными.*
2. **Закрыть порт 5555** на firewall + bind `127.0.0.1`.
3. **Исключить `.env` из electron-builder** + guard-шаг в release-workflow + удалить `.env` из `build/`.
4. **Честный health-check** (MongoDB readyState, 503 при деградации).
5. **Backup:** Atlas snapshots + ежедневный cron + offsite-копия + restore drill.
6. **Миграция вложений** >5 МБ/видео в Cloudinary (или временно — backup `uploads` + дисковый алерт).

Пункты 1–4 — минимальный объём перед ограниченным запуском для друзей. Пункты 5–6 — в течение первых недель после запуска, до роста нагрузки.
